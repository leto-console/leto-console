# Процесс PR

## Ветка и коммиты

- Ветка от свежего `origin/main` (`leto-sync`), имя `<номер-issue>-<краткий-слаг>`.
- В `main` не пушить. PR — только по явной команде.
- Заголовок коммита: `<префикс>: <что сделано>`, императив, без точки, по-английски.
  Тело — по-русски, после пустой строки: «почему».
  Префиксы: `feature:` `fix:` `docs:` `refactor:` `test:` `build:` `ci:` `chore:`
  (`feat:` — отклонение, новые так не писать).
- Единица истории — логическое изменение: сквоить WIP/правки по ревью/опечатки;
  разделять рефакторинг, поведение, документацию, сборку. Код и тесты к нему — вместе.
- Каждый коммит собирается и проходит `ctest` (`leto-check`) — иначе ломается `git bisect`.
- Force-push разрешён только в своей задачной ветке и только `--force-with-lease`.
- Последний абзац сообщения коммита — пометка AI (ниже).

## Пометка AI-сообщений

Первая строка любого сообщения от имени владельца — дословно:

> Написано AI-агентом (OpenHands) по поручению владельца репозитория.

Относится к описаниям PR, комментариям в issues, ответам в тредах ревью — включая
однострочные. В коммите та же фраза идёт последним абзацем. Одна формулировка на все
типы: варианты не находятся поиском.

## Ревью

Мерж требует одного approving review; правила живут в ruleset `Base Rules`
(branch protection API отвечает `Not Found`): `required_approving_review_count: 1`,
`dismiss_stale_reviews_on_push: true`, `required_review_thread_resolution: true`,
разрешены `merge` и `squash`. Обязательные чеки — джобы `build-and-pack`, их список
берётся из ruleset, а не из памяти: в `LetoCore`/`LetoOS` это агрегирующая джоба
`CI Result`, в `leto-console` — матричные сборки `build-and-pack`.

```sh
gh api -X POST repos/{owner}/{repo}/pulls/<N>/requested_reviewers \
  -f 'reviewers[]=leto-console'
```

- Проверять результат по непустому `requested_reviewers` в ответе.
- Ревьюер — владелец `leto-console`; аккаунт агента — автор PR и сам себя одобрить не может.
- Пустой `reviewDecision: REVIEW_REQUIRED` — это «ждёт approve», а не поломка.
- `dismiss_stale_reviews_on_push`: правки отправлять до запроса ревью; пуш после approve
  сбрасывает одобрение и требует повторного запроса.
- Незакрытые треды блокируют мерж наравне с отсутствием approve — отвечать и резолвить самому.

## Мерж и закрытие

```sh
gh pr merge <N> --merge --delete-branch
gh issue close <N> --reason completed     # вручную, после всех PR задачи
```

- Только `Merge commit`: исходные коммиты и SHA сохраняются для `git bisect` и ссылок.
- Не использовать `Closes #N` в PR: одна задача может закрываться несколькими PR
  в разных репозиториях, `Closes` закроет её на первом мёрже.
- Ветку в worktree сначала убрать: `git worktree remove <путь>`, потом `git branch -d`.
- После мержа проверить `main` (сборка/тесты), затем двигать статус — `leto-board`.

## Права

- Запись в `leto-console/*` — только `GH_PROJECTS_TOKEN` (классический, `repo`).
  Fine-grained `GITHUB_TOKEN`/`LETO_GAMES_TOKEN` там всегда дают
  `403 Resource not accessible by personal access token`; роль `write` не помогает.
  В организации `leto-games` те же токены пишут нормально.
- Правка `.github/workflows/*` требует scope `workflow`: без него push отклоняется,
  хотя обычный файл тем же токеном проходит. Проверять до начала работы.
- Права не проверять чтением: репозитории публичные, `GET` проходит анонимно.
  Показательна только пробная запись.
