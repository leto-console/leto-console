# AGENTS.md

Правила для AI-агентов и людей, работающих с LETO. Здесь только проверенные
факты и жёсткие ограничения. Технические задания живут в issues этого
репозитория, а не в этом файле.

## Точка входа

Все задачи — в issues `leto-console/leto-console`. Код разложен по
репозиториям, которые должны лежать рядом в одной папке `$LETO_PATH`:

| Репозиторий | Роль |
| --- | --- |
| `LetoAPI` | замороженный C ABI: `LetoApplication_V1`, `LetoAPI_V1`, `AppBinHeader` |
| `LetoCore` | движок: отрисовка, сцены, инфраструктура игр |
| `LetoOS` | системный слой: `AppLoader`, `SystemSceneManager`, дисплей |
| `leto-console` | точка входа: `Core/Src/Application/System.cpp`, `main()` |

## Обновление клонов

Репозитории проекта — независимые клоны, а не подмодули: ничто их не
синхронизирует. Клон, выданный вместе с окружением, может отставать, при этом
рабочее дерево выглядит исправным.

Перед чтением кода и перед созданием ветки:

```sh
for d in "$LETO_PATH"/*/; do
    git -C "$d" rev-parse --git-dir >/dev/null 2>&1 || continue   # Common/ и Console/ — не репозитории
    git -C "$d" fetch --prune origin || exit 1
    printf '%-14s %s\n' "$(basename "$d")" "$(git -C "$d" status -sb | head -1)"
done
```

- `git status -sb` без `fetch` сравнивает с устаревшим `origin/main`, поэтому
  может не показать отставание или показать меньше реального. Сначала `fetch`,
  потом читать код.
- Если в выводе есть `behind` — только `git merge --ff-only origin/main`.
  Ветки разошлись или дерево грязное: остановиться и сообщить, не разрешать
  конфликт автоматически.
- Утверждение «этого нет в репозитории» проверяется по сети:
  `git ls-remote origin main` или `gh api`. Пустой `find`/`grep` по локальному
  дереву говорит только о локальной копии.
- Ветку задачи отводить от свежего `origin/main`, а не от снимка, полученного
  при старте окружения.

## Сборка

Порядок обязателен: `LetoAPI` → `LetoCore` → `LetoOS` → `leto-console`.
Каждый следующий шаг собирается против артефактов предыдущего.

```sh
export LETO_PATH="$HOME/leto/"          # слэш в конце обязателен

cd "$LETO_PATH/LetoAPI"      && cmake --preset linux-debug
cd "$LETO_PATH/LetoCore"     && cmake --preset linux-debug
cd "$LETO_PATH/LetoOS"       && cmake --preset linux-debug
cd "$LETO_PATH/leto-console" && cmake --preset linux-st7735-debug
```

Зависимости Linux: `cmake`, `ninja-build`, `libsdl2-dev`.

Базовая проверка — существующий набор тестов; проходить должны все:

```sh
cd "$LETO_PATH/LetoOS/build/linux-debug" && ctest --output-on-failure
```

Источник правды по пресетам — `CMakePresets.json` в каждом репозитории.

CI собирает STM32, Windows и Linux (`build-linux` в `LetoOS`). Linux-джоба —
единственное место, где компилируется ветка загрузчика на `dlopen`: STM32 и
Windows её не видят.

## Текущее состояние

Загрузка приложений реализована для STM32, Windows и Unix (Linux, macOS);
заглушек в `LetoOS/include/AppLoader/AppLoader.cpp` больше нет. На Unix игра —
разделяемая библиотека (`.so`, на macOS `.dylib`), которую загрузчик ищет в
`<root>/Apps/<preset>/<Игра>/` и грузит через `dlopen`, а выгружает через
`dlclose` с откатом общей арены по маркеру.

Каталог ищется каскадом, первый найденный выигрывает: `<cwd>/Apps/<preset>/`,
`<cwd>/Apps/`, `$LETO_PATH/Apps/<preset>/`, `$LETO_PATH/Apps/`. Пресет берётся
из `-DLETO_PRESET_NAME`, поэтому `Apps/win-debug/` на Linux не ищется. Ключ
`--game <путь>` отменяет сканирование и грузит указанный `.so` напрямую; путь
канонизируется, потому что относительное имя `dlopen` разрешает только при
`cwd` = каталог библиотеки. Точка входа — переменная `__leto_exec_info__`, а не
функция `Init`: `dlsym(handle, "Init")` возвращает `NULL`.

Чтобы `dlclose` действительно выгружал игру, и хост, и игра собираются с
`-fno-gnu-unique`: glibc держит DSO замапленным навсегда, если тот экспортирует
`STB_GNU_UNIQUE`, а GCC порождает их для локальных статиков в inline- и
шаблонном коде заголовков. Флаг есть в `LetoCore` (опция цели) и в пресетах
`linux-base` репозиториев игр — это не то же самое наследование, поэтому
проверять нужно на финальном `.so`:

```sh
nm -C "$LETO_PATH/Apps/linux-debug/Battleship/libBattleship.so" | grep ' u ' | wc -l   # 0
```

macOS собирается (`#84`), но пресетов `macos-*` в `LetoAPI`/`LetoOS` нет, поэтому
ветка `__APPLE__` проверяется только локально — доводка в #93.

Отладочный запуск игры без прохождения первичной настройки:

```sh
SDL_VIDEODRIVER=dummy LETO_PATH="$LETO_PATH" \
    leto-console --user 0 --game "$LETO_PATH/Apps/linux-debug/Battleship/libBattleship.so"
```

`--game` обрабатывается внутри `if (--user)` (`Core/Src/Application/System.cpp`),
и сцены `GAMES_CENTER`/`APP_SCENE` регистрирует `InitUserScenes()`, которую
вызывает только успешный вход. Поэтому на eeprom без аккаунтов `--game` не
запускал игру, а консоль молча висела в режиме AUTH. Теперь `--user` заводит
тестовый аккаунт, если список пуст; на настроенной консоли поведение не меняется.
`server.eeprom` лежит в `.gitignore`, так что аккаунт живёт только в рабочей копии.

## Инварианты

- `LetoCore` не подключает заголовки `LetoOS`. `SystemSceneManager` объявлен
  в `LetoOS/include/System/`. Заголовки, которым нужен системный слой, лежат
  в `LetoOS/include`.
- Приложение линкует только `LetoAPI` и `LetoCore`, `LetoOS` в игру не
  попадает. Системные части остаются в `LetoOS`, а не переносятся в `LetoCore`
  ради удобства игр.
- `LetoAPI` — замороженный ABI. Несовместимое изменение оформляется как новая
  версия (`V2`), а не правкой `V1`.
- `LetoAPI`, `LetoCore` и `LetoOS` собираются как `STATIC` на всех платформах,
  кроме `WIN32` с заданным `LETO_PATH`. Не переводить на `SHARED`.
- Приложение несёт собственную копию `LetoCore`. Дублирование состояния
  (`VirtualConsole`, `DrawFunctions::defaultFont`) — осознанное решение,
  воспроизводящее поведение прошивки. Не «унифицировать».
  Пользоваться состоянием хоста игра может **только через `LetoAPI`** —
  например, шрифты берутся из `leto_api_v1->Font->FindFont`, а не из
  собственного `GlyphFont::GlobalFonts`. Поэтому распад локального статика в
  заголовке на отдельные экземпляры внутри `.so` (следствие
  `-fno-gnu-unique`) — не дефект: глобальное состояние доступно через
  `LetoAPI`, а копии внутри `.so` живут в своих границах.

## Не трогать без отдельной задачи

- Сборка игр под Linux — #46: сами игры и `game-template` собираются
  пресетом `linux-debug` и грузятся, поэтому «шаблон не собирается» больше
  неверно. Новые игры и фикстуры для них — отдельная задача, не повод
  добавлять их попутно в других PR.
- Termux на паузе: пресеты `termux-*` удалены в #96, код под
  `#ifdef __TERMUX__` (`HttpDisplay.*`, `EEPROM/EEPROM_24C.cpp`) остаётся
  как есть.
- Шрифты остаются в `LetoCore`; вынос в `LetoFont_V1` — отдельная будущая
  задача.

## Процесс

- Названия задач (issues) и заголовки коммитов — по-английски. Тела задач,
  описания PR и тела коммитов — по-русски. То же про заголовки PR.
- Ветка от `main`, имя `<номер-issue>-<краткий-слаг>`.
- В `main` не пушить.
- Ветка удаляется сразу после мержа: `gh pr merge --merge --delete-branch`, либо
  `git push origin --delete <ветка>` и локально `git branch -d <ветка>`
  (ветка в worktree — сначала `git worktree remove <путь>`).
  Мерженые ветки в репозитории не накапливаются.
- PR открывается только по явной команде.
- Ревью запрашивается сразу при открытии PR: мерж требует одного approving
  review, и без него PR не мержится вообще. Смотреть на `reviewDecision` и
  ruleset, а не на практику: `requested_reviewers` в старых PR пуст, потому
  что ревьюер снимается из списка в момент approve, а не потому что его не
  звали.
  - Ревьюер — владелец `leto-console`. Аккаунт агента (`rtimur-ai`) — автор
    PR и сам себя одобрить не может; `leto-console` — единственный, кто
    оставлял ревью в истории `LetoCore`, `LetoOS`, `LetoAPI`, `leto-console`.
  - Условия берутся из ruleset `Base Rules` (не из branch protection: её API
    отвечает `Not Found`, потому что защита живёт в ruleset):
    `required_approving_review_count: 1`, `dismiss_stale_reviews_on_push: true`,
    `required_review_thread_resolution: true`, `current_user_can_bypass: never`,
    обязательный чек — `CI Result`, разрешены только `merge` и `squash`.
  - `dismiss_stale_reviews_on_push` означает: любой пуш после approve сбрасывает
    одобрение. Поэтому новые правки отправляются до запроса ревью, а не после;
    если править пришлось после approve — ревью запрашивается повторно.
  - `required_review_thread_resolution` — незакрытые треды блокируют мерж
    наравне с отсутствующим approve. Отвечать и резолвить их нужно самому.
  - API: `POST /repos/{owner}/{repo}/pulls/{number}/requested_reviewers` с
    `{"reviewers":["leto-console"]}`. Проверять результат по непустому
    `requested_reviewers` в ответе: `GET` того же PR показывает уже
    запрошенного ревьюера.
  - В `reviewDecision` пустое `REVIEW_REQUIRED` — это и есть «ждёт approve»,
    а не ошибка конфигурации.
- Мерж выполняется только методом «Merge commit»: `gh pr merge --merge`.
  Rebase-merge и squash-merge не используются.
- Задача закрывается вручную, а не закрывающими ключевыми словами в PR
  (`Closes #96`). Одна задача может закрываться несколькими PR: #96 — четыре
  PR в четырёх репозиториях. `Closes` закрыл бы задачу на первом же мёрже,
  пока остальные ещё в работе. Закрывать после того, как смержены все PR и
  проверен `main`: `gh issue close <номер> --reason completed`.
- Статус на доске `LETO Console` двигается по ходу работы: `In progress` —
  при взятии задачи, `In review` — при открытии PR, `Done` — при закрытии
  задачи (у всех закрытых задач на доске он такой; у #96 выставился сам).
  Меняется мутацией `updateProjectV2ItemFieldValue`; `gh project` не годится:
  с `GH_PROJECTS_TOKEN` ему не хватает scope `read:org`. Что стоит знать,
  чтобы не искать заново:
  - Id доски, поля `Status` и его опций не хранить ни в этом файле, ни в
    заметках: они привязаны к объекту в конкретной доске и меняются при её
    пересоздании, а устаревший id обнаружится только при вызове —
    `Could not resolve to a node`. Искать по именам: доска `LETO Console`
    (номер 1), поле `Status`, опция по имени.
  - Цепочка: issue → `projectItems` (взять item с `project.number` = 1) →
    мутация на `projectId`, `itemId`, `fieldId`, `value.singleSelectOptionId`.
  - Имя статуса писать как на доске: `In review`, а не `In Review` — опция
    ищется точным совпадением.
  - `gh api --jq` не принимает `--arg`; чтобы подставить имя статуса, пайп
    на `jq -r --arg`.
  - `-f`, а не `-F`: `-F` приводит числовой id опции к числу, и GraphQL
    отвечает `Could not coerce value ... to String`.
- `GITHUB_TOKEN` и другие секреты не печатать в вывод и в комментарии.
- Запись в `leto-console/*` — только `GH_PROJECTS_TOKEN` (классический,
  `scope: repo`). `GITHUB_TOKEN` и `LETO_GAMES_TOKEN` — fine-grained, и они не
  могут писать туда в принципе: эти репозитории принадлежат пользовательскому
  аккаунту `leto-console`, а fine-grained PAT достаёт репозитории только своего
  аккаунта и организаций. Роль коллаборатора (`write`) этому не помогает, ответ
  всегда `403 Resource not accessible by personal access token`. В организации
  `leto-games` те же токены пишут нормально.
- Правка `.github/workflows/*` требует отдельного права сверх записи в
  репозиторий. У классического токена это scope `workflow`: без него push
  отклоняется с `refusing to allow a Personal Access Token to create or update
  workflow ... without 'workflow' scope`, причём обычный файл тем же токеном в
  ту же ветку проходит. Проверять до начала работы, если задача трогает CI.
- Права не проверять чтением: репозитории публичные, и `GET` проходит анонимно
  у любого токена. Показательна только пробная запись.
- Перед коммитом убедиться, что сборка и `ctest` проходят.

## Пометка AI-сообщений

Сообщение, отправленное от имени владельца, начинается с этой строки —
дословно, первой строкой:

> Написано AI-агентом (OpenHands) по поручению владельца репозитория.

Относится к описаниям PR, комментариям в issues, ответам в тредах ревью. В
сообщении коммита та же фраза идёт последним абзацем.

- Одна формулировка на все типы сообщений. Подстановка названия типа («PR»,
  «комментарий», «ответ») порождает варианты: в истории уже четыре разных
  написания на двух языках, а ответы в тредах ревью уходят без пометки вовсе.
  Фиксированный текст проверяется поиском, варианты — нет.
- Пометка нужна и под однострочной репликой: короткие ответы в тредах ревью —
  как раз то место, где она теряется.
- Аккаунт агента совпадает с аккаунтом владельца, поэтому пометка —
  единственный признак того, что текст написан не человеком.

## История коммитов

Единица истории — логическое изменение, а не задача и не функция.

- Сквоить: WIP, правки по ревью, опечатки, форматирование, случайные
  merge-коммиты внутри ветки (мерж PR в `main` — не они).
- Разделять: рефакторинг без изменения поведения, изменение поведения,
  документация, сборка и CI.
- Не разделять: код и тесты к нему; механическую замену в многих файлах.
- Каждый коммит собирается и проходит `ctest` — иначе ломается `git bisect`.
- В своей задачной ветке force-push разрешён (`--force-with-lease`); в `main`
  и в чужих ветках запрещён.
- PR мержится «Merge commit», а не rebase-merge и не squash-merge: исходные
  коммиты и их SHA сохраняются, поэтому `git bisect` и ссылки на коммиты в
  обсуждениях остаются валидными.

### Формат сообщения

Первая строка — `<префикс>: <что сделано>`, императив, без точки в конце.
Заголовок — по-английски, тело — по-русски.
Далее пустая строка и «почему»: описание остаётся в истории навсегда.

- Английский заголовок нужен потому, что первая строка живёт отдельно от
  тела: она попадает в `git log --oneline`, в changelog и в веб-интерфейсы.
  Там кириллица обрезается и хуже переносится, а читают эти места не
  только по-русски.
- Тело остаётся русским: «почему» обсуждается с владельцем по-русски, и
  переводить его — работа с потерей смысла.
- Пометка AI-сообщения — фиксированная русская строка из раздела
  «Пометка AI-сообщений»; правило про английский на неё не
  распространяется.

| Префикс | Когда |
| --- | --- |
| `feature:` | новое поведение или возможность |
| `fix:` | исправление дефекта |
| `docs:` | документация: README, гайды, `AGENTS.md` |
| `refactor:` | структура без изменения поведения |
| `test:` | тесты и фикстуры |
| `build:` | CMake, пресеты, зависимости |
| `ci:` | workflows |
| `chore:` | обслуживание, не влияющее на код |

`feature:` — принятая в репозитории форма, так же префикс назван в README.
`feat:` в истории встречается как отклонение от неё; новые так не писать.
Технически префикс ничем не проверяется — это соглашение, а не CI-гейт.
