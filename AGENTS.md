# AGENTS.md

Правила для AI-агентов и людей, работающих с LETO. Здесь только проверенные
факты и жёсткие ограничения. Технические задания живут в issues этого
репозитория, а не в этом файле.

## Точка входа

Все задачи — в issues `leto-console/leto-console`. Код разложен по четырём
репозиториям, которые должны лежать рядом в одной папке `$LETO_PATH`:

| Репозиторий | Роль |
| --- | --- |
| `LetoAPI` | замороженный C ABI: `LetoApplication_V1`, `LetoAPI_V1`, `AppBinHeader` |
| `LetoCore` | движок: отрисовка, сцены, инфраструктура игр |
| `LetoOS` | системный слой: `AppLoader`, `SystemSceneManager`, дисплей |
| `leto-console` | точка входа: `Core/Src/Application/System.cpp`, `main()` |

## Сборка

Порядок обязателен: `LetoAPI` → `LetoCore` → `LetoOS` → `leto-console`.
Каждый следующий шаг собирается против артефактов предыдущего.

```sh
export LETO_PATH="$HOME/leto/"          # слэш в конце обязателен

cd "$LETO_PATH/LetoAPI"      && cmake --preset linux-debug
cd "$LETO_PATH/LetoCore"     && cmake --preset linux-debug
cd "$LETO_PATH/LetoOS"       && cmake --preset linux-debug
cd "$LETO_PATH/leto-console" && cmake --preset linux-st7735-debug
```

Зависимости Linux: `cmake`, `ninja-build`, `libsdl2-dev`.

Базовая проверка — существующий набор тестов; проходить должны все:

```sh
cd "$LETO_PATH/LetoOS/build/linux-debug" && ctest --output-on-failure
```

Источник правды по пресетам — `CMakePresets.json` в каждом репозитории.

CI собирает только STM32 и Windows. Linux-сборка в CI не проверяется, поэтому
изменения под `#ifdef __LINUX__` нужно собирать и проверять локально.

## Текущее состояние

Загрузка приложений реализована только для STM32 и Windows. На Linux функции
`ScanApps` / `GetBinary` / `UnloadBinary` в `LetoOS/include/AppLoader/AppLoader.cpp`
— заглушки, поэтому GameCenter пуст, а `--game` ничего не запускает. Это
задача #92, не дефект сборки.

## Инварианты

- `LetoCore` не подключает заголовки `LetoOS`. `SystemSceneManager` объявлен
  в `LetoOS/include/System/`. Известные нарушения —
  `LetoCore/include/Input/UserInputTask.hpp` и
  `LetoCore/include/Graphics/IDisplayTasks.hpp`; устраняются в #96.
- Приложение линкует только `LetoAPI` и `LetoCore`, `LetoOS` в игру не
  попадает. Системные части остаются в `LetoOS`, а не переносятся в `LetoCore`
  ради удобства игр.
- `LetoAPI` — замороженный ABI. Несовместимое изменение оформляется как новая
  версия (`V2`), а не правкой `V1`.
- `LetoAPI`, `LetoCore` и `LetoOS` собираются как `STATIC` на всех платформах,
  кроме `WIN32` с заданным `LETO_PATH`. Не переводить на `SHARED`.
- Приложение несёт собственную копию `LetoCore`. Дублирование состояния
  (`VirtualConsole`, `DrawFunctions::defaultFont`) — осознанное решение,
  воспроизводящее поведение прошивки. Не «унифицировать».

## Не трогать без отдельной задачи

- Сборка игр под Linux и шаблон игры — #46. Шаблон сейчас не собирается:
  `DrawText` переименован в `DrawString`. Это не повод чинить его попутно
  в других PR.
- Termux на паузе: пресеты `termux-*` и код под `#ifdef __TERMUX__`
  (`HttpDisplay.*`, `EEPROM/EEPROM_24C.cpp`) остаются как есть.
- Шрифты остаются в `LetoCore`; вынос в `LetoFont_V1` — отдельная будущая
  задача.

## Процесс

- Ветка от `main`, имя `<номер-issue>-<краткий-слаг>`.
- В `main` не пушить, ветки после мержа не удалять.
- PR открывается только по явной команде.
- `GITHUB_TOKEN` и другие секреты не печатать в вывод и в комментарии.
- Перед коммитом убедиться, что сборка и `ctest` проходят.

## История коммитов

Единица истории — логическое изменение, а не задача и не функция.

- Сквоить: WIP, правки по ревью, опечатки, форматирование, merge-коммиты.
- Разделять: рефакторинг без изменения поведения, изменение поведения,
  документация, сборка и CI.
- Не разделять: код и тесты к нему; механическую замену в многих файлах.
- Каждый коммит собирается и проходит `ctest` — иначе ломается `git bisect`.
- В своей задачной ветке force-push разрешён (`--force-with-lease`); в `main`
  и в чужих ветках запрещён.
- PR из нескольких коммитов мержится rebase-merge. Squash-merge — только если
  коммит действительно один.

### Формат сообщения

Первая строка — `<префикс>: <что сделано>`, императив, без точки в конце.
Далее пустая строка и «почему»: описание остаётся в истории навсегда.

| Префикс | Когда |
| --- | --- |
| `feature:` | новое поведение или возможность |
| `fix:` | исправление дефекта |
| `docs:` | документация: README, гайды, `AGENTS.md` |
| `refactor:` | структура без изменения поведения |
| `test:` | тесты и фикстуры |
| `build:` | CMake, пресеты, зависимости |
| `ci:` | workflows |
| `chore:` | обслуживание, не влияющее на код |

`feature:` — принятая в репозитории форма, так же префикс назван в README.
`feat:` в истории встречается как отклонение от неё; новые так не писать.
Технически префикс ничем не проверяется — это соглашение, а не CI-гейт.
